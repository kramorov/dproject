# Вендор → OEM: наследование моделей с транскодированием опций

Назначение: вендор (например, AOX) описывает приводы и блоки управления
один раз; OEM-продавцы (Архимед и др.) продают те же изделия под своими
названиями и артикулами. Правка данных вендора обновляет всех продавцов —
кроме полей, которые продавец переопределил явно.

Статус: **механизм не реализован**. Ниже — описание прототипа из `valve_data`
и анализ, что из этого нужно заложить в слотовую модель сейчас, а что можно
добавить позже без переделки.

---

## 1. Прототип в valve_data (арматура)

Рабочий механизм наследования (приложение сильно отстало от паттернов, но
эта часть работает):

- **`ValveLine.original_valve_line`** — self-FK (`null=True`,
  `on_delete=SET_NULL`, `related_name='derived_valve_lines'`). У серии
  вендора — null; у OEM-серии — ссылка на вендорскую серию.
- **`ValveLineInheritanceMixin.get_field_value_with_fallback(field_name,
  show_data_source, max_recursion=5)`** — рекурсивный fallback: если
  локальное значение поля «пустое» (`None` / пустая строка / несохранённый
  FK) — берётся значение из `original_valve_line`, дальше по цепочке.
  `show_data_source=True` возвращает `{value, source, comment}` — кто
  источник значения.
- **`ValveLineDataGettersMixin`** — обёртки `effective_name()`,
  `effective_code()`, `effective_description()`, `effective_item_code_template()`
  и т.д. для всех наследуемых полей.
- **Админка** — поле `original_valve_line` в списке/форме + подсветка
  унаследованных значений (источник).
- **Транскодирование** = OEM-запись переопределяет только свои поля
  (артикул, название, шаблон кодировки); всё остальное наследуется из
  вендора. Изменение вендорской записи мгновенно отражается у всех
  OEM-потомков, не переопределивших поле.

Суть механизма — **послойный per-field fallback по self-FK**, а не копия
данных (копии рассинхронизируются — `ea_model_line_admin.copy_related_options`
в ЭП так и работает, и это проблема, а не решение).

---

## 2. Как это ложится на слотовую модель БУ/приводов

Оси вендор/OEM:

| Сущность | Вендорская запись | OEM-запись (переопределяет) | Наследуется (fallback) |
|---|---|---|---|
| Тип БУ (`ControlUnit`) | AOX: code/name/kind/location/M2M/шаблоны | свой `code`/`name`/`brand` (Архимед), шаблоны названия | kind, location, control_voltage, signal_power, accepts/emits/protocols/capabilities |
| Опция слота (`CuSlotOption`) | AOX: код, кодировка, типизированная нагрузка | свой код + `encoding`/`ext_encoding` (артикул OEM) | kind, нагрузка (сигнал/дисплей/резьба/…), имя |
| Серия ЭП (`ElectricActuatorModelLine`) | AOX-серия | Архимед-серия (свой код/бренд) | характеристики привода, разрешённые опции |
| Строка матрицы (`CuMatrixEntry`) | скоуп на AOX-серию | строки со скоупом на Архимед-серию (перекрытие/na) | — (резолвер скоупов уже умеет перекрытие) |

Принципы:

1. **Коды вендорских сущностей — стабильные ключи маппинга** (уже
   соблюдается: `ControlUnit.code`, коды опций, коды серий).
2. **OEM-сущности — отдельные записи**, ссылающиеся на вендорскую;
   вендорские записи под OEM никогда не переписываются.
3. **Кодировка артикула переопределяется на OEM-уровне**: `encoding`/
   `ext_encoding` у OEM-опции (справочно) и у OEM-строки матрицы
   (приоритет строки уже реализован в резолвере: `_row_payload`).
4. **Снимок и правила инвариантны**: значения — коды опций (коды слотов и
   опций общие для вендора и OEM), правила работают по кодам — им не нужна
   ось вендор/OEM.

## 3. Что нужно ввести в слотовую модель сейчас

**Обязательного — ничего.** Механизм — «слой оригиналов» поверх
существующих моделей: self-FK + fallback-геттеры. Добавление поля позже —
дешёвая `AddField`-миграция без дата-переноса. Текущие модели (узел/слот/
опция/матрица/правило/снимок) менять **не потребуется** — наследование не
затрагивает их структуру.

Резервы, которые стоит соблюдать уже сейчас (конвенции, а не схема):

- **Коды-ключи маппинга не менять** без миграции данных: `ControlUnit.code`,
  коды опций (`IND_OPEN_LED`…), коды серий. Аналог сегодня: `legacy_cu`
  (1:1 на legacy-справочник) — `original_*` станет вторым таким маппингом.
- **ОEM-переопределения кодировок — строками матрицы** (механизм приоритета
  уже есть), а не правкой вендорских опций.
- **Новые слоты/опции описываются только вендором**; продавцы не создают
  собственные слоты — только свои опции/строки/кодировки со ссылкой
  `original_*`.

Когда появится реальный вендорский набор данных (AOX → Архимед + ещё
продавец), план ввода (порядок):

1. Перенести миксин `get_field_value_with_fallback` из valve_data в `core`
   (обобщённый, с `original_field`-конфигурацией) — без моделирования.
2. `ControlUnit.original_control_unit` self-FK (null, SET_NULL) +
   effective-геттеры; OEM-БУ = новая запись с `brand=Архимед`,
   `original_control_unit=AOX-БУ`, свой code/name/шаблоны.
3. `CuSlotOption.original_option` self-FK (null) — OEM-опция наследует
   нагрузку/kind, переопределяет кодировку/имя.
4. `ElectricActuatorModelLine.original_model_line` self-FK (в ЭП) +
   расширение `resolve_slots`/`_scope_matches`: если для OEM-серии строк
   нет — цепочка `original_model_line` (наследование строк вендорской
   серии с перекрытием строк OEM-серии).
5. Админка/структура: показ источника значения (`show_data_source`), как в
   valve_data.

## 4. Проверка консистентности (как проверим, что механизм работает)

- Правка вендорского БУ (например, добавили протокол) → пакет OEM-БУ
  Архимеда изменился без правок Архимеда.
- Переопределение OEM-кодировки (encoding опции) → артикул Архимеда
  собрался со своими кодами, физика осталась AOX.
- Правка вендорской серии → доступность опций у всех OEM-продавцов
  обновилась; локальные na/перекрытия продавца сохранились.
