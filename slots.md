# Узлы, Слоты и Матрицы — конфигуратор БУ (ea_control)

Назначение: конфигурирование сложного оборудования без комбинаторного взрыва
в БД и без хардкода логических правил. Текущая реализация отлаживается на
блоке управления электропривода (БУ) в приложении `ea_control`.

---

## 1. Паттерн

### Золотое правило

- **Физика типизируется**: справочники и физические сущности — обычные
  Django-модели с типизированными полями (скаляры + FK/M2M на справочники),
  без композитных данных.
- **Связи и ограничения универсальны**: логика доступности, дефолтов и
  динамики управляется сквозными паттерн-моделями, одинаковыми для любых
  типов данных.

### Роли (словарь)

- **Узел (Node)** — логическое объединение параметров: группировка слотов
  в дерево конфигуратора (например, «Датчики» — все вопросы о типе
  датчиков); вкладывается через `parent`.
- **Слот (Slot)** — описание сущности конфигурации **без строки в БД**:
  объявляет тип сущности (для object — источник-справочник `source`),
  точку в дереве (`section`), режим выбора и обязательность; не хранит
  выбранное значение и не дублирует физику — она в справочнике-источнике.
- **Опция (Option)** — физическое значение слота: для object-слотов —
  конкретная запись справочника-источника (срез значений), для value —
  имя/описание; несёт типизированную полезную нагрузку по `kind`.
- **Матрица (MatrixEntry)** — доступность опции в точке контекста (Паттерн А).
- **Правило (Rule)** — динамика UI по выбранному значению (Паттерн В).
- **Снимок (Snapshot)** — плоский результат `{slot_code: value}`.

Иллюстрация «Датчики»: семь слотов узла SENSOR — семь сущностей («тип
датчиков концевых основных» и т.д.), ни одной модели в БД; опции — записи
`CuFeedbackDevice` (MECH/ENC/THERMO/PTC). Новая сущность добавляется слотом
без миграции — пока у неё нет собственных атрибутов вне справочника
(иначе нужна настоящая модель — граница применимости паттерна).

Вложенность жёсткая: **узел → слот → опция**. Вложенных слотов нет: слот —
лист узла, опция — лист-значение слота.

Слот принадлежит ровно одному узлу (инвариант 1:1): позиция слота в дереве —
презентация; значение живёт в снимке, доступность — в матрице, динамика — в
правилах. Если слот нужно показать в двух местах — вводим ссылочные узлы
(read-only отображение чужих слотов), а не M2M-владение. Несколько слотов
могут ссылаться на один справочник — это штатный способ «горизонтальной
гибкости»: два слота = две независимые точки со своими строками матрицы и
правилами.

### Флаги слота: «Обязательный», «Режим выбора», «Род значения»

Три скалярных флага `AbstractConfigSlot` (`models/abstract.py`) полностью
описывают «розетку»: слот не хранит выбранное значение — флаги объявляют,
**как** в него выбирать и **что** значит выбранное. Редактируются в
«Конфигураторе опций» (форма слота, с popover-подсказками) и попадают в
пакет конфигуратора (`cu_package._slot_payload`).

#### «Обязательный» (`required`, bool, default False)

Смысл: в слоте должна быть хотя бы одна доступная опция; none-строка
«Нет» считается доступной опцией (формулировка из `EaSignalSlot.required`).
Флаг декларативный — контракт слота, а не блокировка выбора.

Как используется:

- пакет (`cu_package`) отдаёт `required` в payload слота;
- фронт (Превью БУ) выводит метку «обязателен» в шапке слота, если
  `slot.required` **или** правило `require` сделало слот обязательным
  (`slotState().required`);
- динамическая обязательность — правило (Паттерн В) с действием
  `require`: `cu_rules.apply_rules` ставит `state['required']=True` в ответ
  на выбор значения слота-условия;
- в сиде: `required=True` у `CU_LOCATION`, `CMD_WIRING`,
  `LOCAL_CONTROL_DESIGN`, `CU_POWER_SUPPLY`, `CU_CABLE_GLANDS`;
  `MOTOR_STARTER` — явно `False`; остальные — дефолт `False`.

Серверной валидации «обязательный слот пуст → ошибка» пока нет: флаг
работает как подсказка UI и спецификация; жёсткую проверку можно добавить
в валидацию снимка (кандидат рядом с bundle/conflicts).

#### «Режим выбора» (`selection_mode`, ConfigSelectionMode, default single)

Семантика выбора: сколько опций можно выбрать и в какой форме значение
попадёт в снимок.

- `single` — одна опция (radio). Значение в снимке — строка: код опции.
- `xor` — «одна из взаимоисключающих»: выбирается ровно одна опция, и
  альтернативы по смыслу исключают друг друга (в отличие от single, где
  «одна» — просто механика выбора). На фронте рендерится как single
  (radio); различие — семантическое.
- `multi` — несколько одновременно (checkbox); значение — список кодов.
  Наследие `EaSignalSlot.multi_choice` (слот CMD: команды О/С/З + Remote
  + Lock в одном слоте). **Исключение, а не правило** (решение
  2026-11-01): слот в общем случае держит один тип значения; `multi`
  применяется осознанно и только там, где набор значений действительно
  нужен. В текущем сиде БУ не используется — команды разведены по
  отдельным слотам CMD_*.

Режим `bundle` удалён из словаря (решение 2026-11-01): как режим слота
он был декларативен — по нему ничего не ветвилось. Сама пакетная
механика осталась на строках матрицы: `bundle` — это не режим выбора, а
«именованный фрагмент конфигурации» (см. «Решение: два рода слота…»).

Как используются сейчас: в демо-данных БУ 42 слота; единственный
не-`single` — `PHASE_PROTECTION` (`xor`, осознанно, слот пользователя
2026-11-02). `multi` не используется. Фронт: `multi` → чекбоксы,
остальные — radio; режим показывается бейджем в шапке слота (Превью БУ).

#### «Род значения» (`slot_kind`, ConfigSlotKind, default value)

Договорились (2026-11-01): слот бывает **либо `value`, либо `object`**;
`subtype` остаётся зарезервированной осью паттерна (см. «Решение: два рода
слота…» ниже).

- `value` — простое значение: опция сама несёт имя/описание/кодировку,
  типизированной нагрузки нет. Kind опции value-слота — `value` «Значение»
  (строковое значение: живёт в `name`/`code`) либо `none` «Нет»
  (мета-значение «ничего не выбрано»); `pair` «Пара контактов» выведен
  из употребления (2026-11-02).
- `object` — объектное значение: слот объявляет справочник-источник,
  опции — срез записей этого справочника; имя/описание берутся из
  справочника, в опции не вводятся (исключение — none-опция «Нет»).
- `subtype` — подтип оборудования (`EquipmentType`): значение слота —
  узел классификатора, выбор меняет тип конфигурируемого изделия
  (схему). Зарезервирован; в отладке БУ не используется.

Как используется: пакет отдаёт `slot_kind` в payload слота; фронт ветвится
на две карточки опций (value — имя/описание, object — выбор записи
справочника-источника + превью name/description записи). Данные приведены
(§4.3): 39 object-слотов с источником, 3 value-слота (TURN_COUNTER/
MOTOR_STARTER — none-опции; PHASE_PROTECTION — value-пара с xor-выбором).

### Решение: два рода слота и правила выбора/видимости (2026-11-01)

Образцовая модель: правила ниже вырабатываются на БУ и переезжают в
`core` вместе с абстракциями (§5.1); на других данных должны работать без
изменений.

**Слот — либо значение, либо объект.**

- `value`: опции — произвольные значения (строки); значение — в `name`
  (отображение) и `code` (ключ в снимке), типизированной нагрузки нет.
  Kind опции — `value` «Значение» либо `none` «Нет»; `pair` выведен из
  употребления (2026-11-02).
- `object`: слот объявляет справочник-источник (возврат к
  `options_config.model` исходного спека; поле `CuSlot.source`); опции
  слота — фиксированный набор записей этого справочника (срез значений),
  без собственных name/description/kind — физика в справочнике,
  конфигуратор её не дублирует. Исключение — none-опция «Нет»
  (kind=none, несёт только имя): это мета-значение «ничего не выбрано»,
  а не запись справочника. Сервер выводит kind опции из source слота
  (`SLOT_SOURCE_PAYLOAD`; сериализатор + `CuSlotOption.clean`).
- Фронт — две карточки опций слота: value (имя/описание + kind
  «Значение»/«Нет») и object (выбор записи справочника-источника +
  encoding/ext_encoding, без полей описания; чекбокс «Опция „Нет“»).
  [реализовано — EaControlStructure.vue]

**Матрица: std/opt/na на каждую опцию слота.**

- std — максимум один на слот для single/xor (реализовано в
  `cu_unit_matrix.apply_changes`, в пределах выбранного напряжения);
  для multi — несколько std допустимы (несколько предвыборов).
  Bare-строки (без опции) в счёте std не участвуют.
- Пакеты строк матрицы (`bundle`-код) — **именованный фрагмент
  конфигурации**: набор пар «слот → опция» из разных слотов (частичный
  снимок), выбираемый атомарно. Не режим слота, а свойство строк
  матрицы. В сиде — пакет MWG (опция АУМА): позиционная ОС MWG = «нет»
  концевых и моментных в обе стороны (5 строк в 5 слотах). Целостность —
  `validate_selection` (выбрана строка пакета → выбраны все доступные
  строки пакета). Кандидат на вынос в отдельную сущность паттерна
  «Пакет» (code/name_i18n + члены; доступность производная: пакет
  доступен, если доступны все члены) — при переезде в core или
  появлении второго пакета; пока оставляем строковую механику.
- Все опции слота na → выбора нет: слот скрывается целиком. [реализовано
  — Превью БУ: `availableOptions(slot).length`]

**Видимость и редактируемость на модель БУ.**

- Слот: `hide`/`show`/`block` правилами (реализовано).
- Узел: производно — узел скрыт, если скрыты все его слоты; отдельные
  правила на узлы не вводим, пока не понадобятся. [кандидат]
- Один std и нет opt-опций → слот без выбора: показывается как
  read-only («std: X», без inputs). [реализовано — Превью БУ:
  `slotReadonly(slot)`]

**Приведение данных (выполнено 2026-11-01):** слоты с payload-опциями —
`slot_kind=object` + источник (40 слотов, сид `slot_flags`; LOCAL_CONTROL →
local_control, INDICATOR → display — опции ссылаются на записи
справочников; ACCESS_DEVICE → access_device, общая модель ЭП
`EaAccessDeviceOption`; «Датчики» — 7 слотов → device); `value` — слоты с
none-опциями (2: TURN_COUNTER/MOTOR_STARTER). Bare-строки матрицы с
полезной нагрузкой — кандидат на ревизию (вторая точка правды вне
справочников).

### Три паттерна

- **Паттерн А — Матрица.** Доступность опции по контексту (скоуп + координаты):
  `availability` std/opt/na, `is_default`, `bundle`, `conflicts`.
- **Паттерн Б — Цена.** Вне scope конфигуратора; отдельная сущность по общему
  паттерну, не реализована в `ea_control`.
- **Паттерн В — Правило.** `when {slot, operator, value}` → `then {action,
  target_slot}`: show/hide/block/require/set_default.

### Граница «узел дерева vs опция изделия»

БУ — **не узел дерева**, а опция слота `control_unit` (kind=`object`).
Доступность и дефолты для конкретного БУ задаются строками матрицы со скоупом
`control_unit`, а не отдельным деревом на каждый БУ.

## 2. Текущие модели — приложение `ea_control`

### Абстракции (`models/abstract.py`)

Общие поля и логика; связные поля (FK/M2M) объявляет наследник.

- `AbstractConfigNode` — узел: `code`, `key` (стабильный UUID для синхронизации, read-only),
  `name`, `parent` (self-FK), `description`,
  `sorting_order`, `is_active`.
- `AbstractConfigSlot` — слот: `code`, `key` (стабильный UUID), `name`, `selection_mode`
  (single/multi/xor), `slot_kind` (value/object/subtype), `required`,
  `description`, `sorting_order`, `is_active`.
- `AbstractSlotOption` — опция: `code`, `key` (стабильный UUID), `kind`, `name`,
  `encoding`/`ext_encoding`,
  `description`, `sorting_order`, `is_active`.
- `AbstractSlotMatrixEntry` — строка матрицы: `availability` (std/opt/na),
  `is_default`, `bundle`, `conflicts` (M2M self), `encoding`/`ext_encoding`,
  `name`, `description`, `sorting_order`; `save()` ставит std → is_default.
- `AbstractSlotRule` — правило: `when_operator`, `when_value` (JSON), `action`
  (show/hide/block/require/set_default), `action_value` (JSON), `priority`,
  `is_active`.
- `AbstractConfigSnapshot` — снимок: `config_snapshot` (JSON) + методы
  `set_option`/`get_option`/`apply_defaults`/`full_code`.

Словари: `ConfigSelectionMode`, `ConfigSlotKind`, `ConfigAvailability`,
`ConfigRuleAction`, `ConfigRuleOperator`.

### Конкретные модели (`models/cu_config.py`)

- `CuSectionNode(AbstractConfigNode)` — узел-секция БУ.
- `CuSlot(AbstractConfigSlot)` — слот БУ, + `section` (FK → CuSectionNode),
  `source` (CuSlotSource — источник значений object-слота; value — пусто),
  `clean()`: object обязан объявить источник, value — не может.
- `CuSlotOption(AbstractSlotOption)` — опция БУ, + `slot` (FK → CuSlot) и
  типизированные нагрузки по `kind`:
  - `signal` → ровно одно из `control_signal`/`feedback_signal`/`protocol`;
  - `heater` → `heater_supply`; `power` → `signal_power`; `logic` →
    `control_logic`; `unit` → `control_unit`
    (только слот `control_unit`); `unit_kind` → `control_unit_kind`
    (класс БУ из `ControlUnitKind`); `location` → `location_option`
    (слот `CU_LOCATION`); `cable_gland` → `cable_gland_set` (общая модель
    ЭП `electric_actuators.CableGlandHolesSet`); `value`/`none` → только
    `name` (опции value-слота); `pair` — устаревший;
  - `device` — датчик по умолчанию.
- `CuMatrixEntry(AbstractSlotMatrixEntry)` — доступность: `slot`/`option` FK,
  скоуп (`brand`/`model_line`/`body`/`model_line_item` — ровно один),
  контекст (`control_unit`/`power_supply`/`mode`), полезные нагрузки
  (`control_signal`/`feedback_signal`/`protocol`/`device`/`heater_supply`).
  CheckConstraints «один скоуп» и «одна нагрузка»; строки с пустым скоупом —
  профиль (дефолты) типа БУ.
- `CuSlotRule(AbstractSlotRule)` — `when_slot`/`target_slot` FK + `evaluate()`.

### Физическая модель БУ (`models/control_unit.py`)

- `ControlUnit` — тип БУ: `brand`, `code` (уникален в рамках бренда),
  `name_i18n`, `kind` (FK → справочник `ControlUnitKind`: NONE/BASIC/
  INTEGRATED/POSITIONER), неизменяемый `key` (короткий UUID
  `uuid.uuid4().hex[:16]`, генерится в `save()`, read-only в API), M2M
  `accepts`/`emits`/`protocols`/`capabilities`, шаблон названия
  `name_template` (+ `name_template_i18n`; описание/спецификация
  шаблонами не задаются — их считает генератор `cu_description`),
  `legacy_cu` (1:1 маппинг на legacy справочник; сид идентифицирует БУ по
  `legacy_cu`, а не по `code`/`key`). Поля `location`/`control_voltage`/
  `signal_power` из модели убраны (2026-10-29): БУ описывает сигналы и
  датчики — описание подходит к разным моделям и напряжениям серии.
  Размещение — слот `CU_LOCATION` (опции kind=`location` →
  `CuLocationOption`); напряжение/схема цепей — слот `CMD_WIRING`.
  Привязка БУ к model_line_item — отдельная задача (§4.1, опция со своей
  кодировкой через through-модели).

### Справочники физики (`models/dictionaries.py`)

Копии справочников ЭП (изоляция от `electric_actuators`): `CuControlSignalForm`
(формы ВХОДНЫХ сигналов: сухой контакт с внутренним опросом / потенциал AC/DC
/ петля 4–20 мА) и `CuFeedbackSignalForm` (формы ВЫХОДНЫХ: сухой контакт реле
/ петля / потенциометр), `CuControlSignal`, `CuFeedbackSignal`,
`CuCommProtocol`, `CuFeedbackDevice`, `CuHeaterSupply`, `CuLocationOption`,
`CuCapability`, `CuLocalControlType`, `CuDisplayType`, `CuUnitPowerSource`.

Классифицирующие поля переведены с TextChoices на **общие справочники ЭП**
(прецедент — `CableGlandHolesSet`/`EaFeedbackDeviceKind`):

- категория формы: `CuControlSignalForm.category` и
  `CuFeedbackSignalForm.category` → `EaSignalFormCategory` (одна общая:
  объединение категорий ЭП `contact/analog/discrete/resistance` и БУ
  `dry_input/voltage_ac/voltage_dc/current_4_20/dry_output`);
- роль: `CuControlSignal.role` → `EaControlSignalRole`; `CuFeedbackSignal.role`
  → `EaFeedbackSignalRole`;
- норма контакта: `CuFeedbackSignal.contact_normal` → `EaContactNormal`;
- транспорт: `CuCommProtocol.transport` → `EaProtocolTransport` (канон —
  нижний регистр: `rs485`/`ethernet`/`current_loop`/`h1`/`other`);
- устройство ОС: `CuFeedbackDevice.kind`/`technology` →
  `EaFeedbackDeviceKind`/`EaFeedbackTechnology`.

Единые наборы значений — константы в `electric_actuators.models`
(`FEEDBACK_DEVICE_KINDS`, `FEEDBACK_TECHNOLOGIES`, `SIGNAL_FORM_CATEGORIES`,
`CONTROL_SIGNAL_ROLES`, `FEEDBACK_SIGNAL_ROLES`, `CONTACT_NORMALS`,
`PROTOCOL_TRANSPORTS`) и `POLARITIES` в `ea_control.models.cu_power`.
`clean()`/валидация работают по `.code`. Собственная классификация
`CuControlSignal.category` (discrete/analog) и `CuFeedbackSignal.category`
(contact/analog) осталась CharField — это внутренняя ось сигнала, не общий
справочник. Миграции применены (ea_control 0016–0019, electric_actuators
0078–0081), бэкфилл без NULL; `makemigrations` — «No changes».

Дискретные командные сигналы из `EaControlSignal` намеренно не переносятся в
`CuControlSignal` (он только аналоговый) — команды выражены слотами CMD_* +
логикой + схемой цепей.

### Схемотехника цепей управления (`models/cu_power.py`)

- `CuSignalPowerSource` (INTERNAL/EXTERNAL + флаг ``internal`` — встроенный
  источник выдаёт опорное напряжение);
- `CuSignalPower` (схема цепей: источник × напряжение × форма входа ×
  полярность; unique_together + условный UniqueConstraint для пар без формы
  входа — SQLite с NULL в индексе не защищает);
- `CuPolarity` (PNP/NPN/двунаправленный/не применимо — с подробным
  объяснением терминов в help_text) — `CuSignalPower.polarity` → FK;
  callable-дефолты FK возвращают **pk (int)**, а не инстанс (иначе
  SQLite-миграция падает на `_remake_table`);
- `CuControlLogic` (импульсная/потенциальная/настраиваемая). Напряжение — FK
  `params.PowerSupplies`.

### Питание БУ и кабельные вводы

- Слот `CU_POWER_SUPPLY` «Питание БУ» → справочник `CuUnitPowerSource`
  (SHARED_CABLE «От цепей питания привода (общий кабель)» / SEPARATE_CABLE
  «Отдельный кабель питания БУ»). Дефолт кодируется профильными строками
  матрицы типа БУ (встроенный — общий std / отдельный na; навесной —
  отдельный std / общий opt); встроенным слот скрыт правилом.
- Слот `CU_CABLE_GLANDS` «Кабельные вводы БУ» → **общая модель ЭП**
  `electric_actuators.CableGlandHolesSet` (набор отверстий `cg1..cg4` →
  `params.ThreadSize`; записи БУ: 2×M20x1.5 / 2×M25x1.5 / 2×PG16 /
  1×1½" NPT + 2×¾" NPT; опции слота — старые коды `2хM20*1,5` /
  `2хM25*1,5` / `1x11/2NPT+2x3/4NPT` + `CG_PG16` — дубли CG_* вычищены
  2026-11-02, сид ищет набор по составу cg1..cg4). Для встроенного БУ
  слот скрыт правилом (вводы — у привода).
- **«Чьи отверстия для подбора КВ» — производное, не слот**: `PU_SHARED`
  (общий кабель) → отверстия корпуса привода, вводы БУ не используются
  (правило hide `CU_CABLE_GLANDS`); `PU_SEPARATE` → отверстия БУ (show).
  Отдельный справочник «Используются КВ» не вводим (вторая точка правды
  разошлась бы с выбором питания). Исключение: навесному БУ (`CU_INT_O`)
  вводы БУ показываются всегда (show с priority 1 перебивает PU_SHARED-hide)
  — сигналы заходят в БУ и при общем кабеле питания. «Корпус+Блок» —
  агрегация при подборе КВ (у привода корпусные вводы есть всегда),
  считается кодом сборки, не хранится.

### Структура «Дистанционное управление»

Узел `CONTROL_SIGNALS` → подузел `CMD_INPUTS` «Дистанционное управление»:

- `CMD_WIRING` (single, required) — «Схема цепей управления»: **опция =
  пара источник × напряжение × форма × полярность** (`CuSignalPower`,
  kind=power). Активность (сухой контакт/потенциал) и полярность — атрибуты
  пары, не отдельные слоты. Пара вместо каскада слотов: недопустимые
  сочетания невыразимы в принципе, описание БУ — одна матрица слота вместо
  трёх + связок. К каскаду вернуться, если оси размножатся комбинаторно.
- `CMD_OPEN` / `CMD_CLOSE` / `CMD_STOP` / `CMD_ESD` (single) — сигналы
  дистанционного управления. **Опция слота = логика работы сигнала**
  (дискретный = импульс с самоподхватом / продолжительный = потенциал /
  настраиваемый — `CuControlLogic`, kind=logic) + явная опция
  **«Отсутствие сигнала»** (kind=none, в основном для СТОП, доступна в
  каждом слоте). Состав сигналов — профильные строки конкретного БУ.
- **Набор сигналов — опции схемы**: координата `signal_power` у
  `CuMatrixEntry` — строки с конкретной схемой перекрывают профильные
  («у позиционера дискретные команды только при внешней схеме 24 В DC»).
  Резолвер: без выбранной схемы строки с координатой не применяются.
- ESD — одна команда; направление (аварийно открыть/закрыть) настраивается
  в меню БУ, в конфигураторе не выбирается.
- Удалены: слоты `CMD` (multi), `SIGNAL_POWER_SOURCE`, `CONTROL_LOGIC`,
  `SIGNAL_TYPE`, справочник `CuSignalType`; `CuControlSignal` больше не
  хранит `voltage`/дискретные формы (остались аналоговые уставки).

### Узел «Общие параметры»

Узел `GENERAL` «Общие параметры»: слот `CU_LOCATION` (single, required)
«Размещение БУ» — **опция = справочник `CuLocationOption`** (kind=`location`:
встроенный/навесной/удаленный — коды BUILT_IN/MOUNTED/SEPARATE;
код MOUNTED — переименован из INTEGRATED 2026-11-08, конфликт с
ControlUnitKind.INTEGRATED устранён). Доступность — профильные строки
матрицы типа БУ.
Поля `location`/`control_voltage`/`signal_power` из модели `ControlUnit`
убраны: БУ описывает сигналы и датчики без привязки к модели и напряжению
привода; привязка к model_line_item — отдельная задача (§4.1).

### Узел «Датчики» (тип датчика, не сигнал ОС)

Узел `SENSOR` «Датчики» — осознанно отдельная ось: **тип датчика**
(механический/электронный/нет), а не сигнал ОС. Семь слотов
(slot_kind=object, источник `device` → справочник `CuFeedbackDevice`):
концевые/путевые/моментные × основные/дополнительные
(`END_SWITCHES_SENSOR_MAIN/EXT`, `WAY_SWITCHES_SENSOR_MAIN/EXT`,
`TORQUE_SWITCHES_SENSOR_MAIN/EXT`) + `THERMO_SENSOR` «Тип датчика
теплозащиты» (термореле `THERMO` / PTC-термистор `PTC_THERMISTOR` / нет).
Опции каждого слота — срез устройств `MECH` «Механические» / `ENC`
«Энкодер» + none «Нет датчика»; коды опций с префиксом слота (`END_MAIN_*`
и т.д.) — одни и те же записи устройств используются в разных слотах.
Восстановлено из исходного дизайна (git e0a1849, секция SENSOR) после
ложной чистки как «stale»; сид больше не удаляет слоты осознанного
дизайна (в `stale_slots` — только явный мусор). Сигнальные слоты
концевых/путевых/моментных выключателей остаются в узле FEEDBACK —
сигнал и тип датчика разведены по разным узлам.

### Решение: «Датчики» и «Сигналы ОС» — разводить (2026-11-06)

Пересмотр узлов `SENSOR`/`FEEDBACK`: в опросных листах (ОЛ) датчик и сигнал
идут **разными строками** («Выключатели: концевые/…/моментные,
одиночные/двойные»; «Сигнализация состояния: Открыто/Авария, 24 В»), а
описание БУ должно повторять тексты ОЛ (цель 1 — фильтры и LLM-разбор).
Физически датчик и сигнал связаны, но это отношение, а не одна сущность:

- **датчик без сигнала** — штатная ситуация (потенциометр установлен, но
  ОС не заведена; термореле есть, выхода нет);
- **сигналов не бывает больше, чем датчиков** — сигнал требует датчик;
- **один датчик несёт один сигнал** (1:1), но у разных датчиков он разный
  (основной — мокрый контур 220 В, дополнительный — сухой 250 В).

Отсюда:

- **Вид → узел.** «Концевые» / «Промежуточные» / «Моментные» / «Положение» /
  «Теплозащита» / «Состояния» — узлы (группы слотов), а не префиксы в коде
  слота (`LIMIT_SWITCHES_OPENED/CLOSED`). Под узлом висят разномастные слоты.
- **Основной/дополнительный → слоты.** Один вид может нести два датчика
  разных типов (основной энкодер для БУ + дополнительный двойной
  механический для жёсткой ОС) — поэтому «осн/доп» это два слота под узлом,
  каждый — срез справочника датчиков.
- **Сигнал — не отдельная ось.** Сухой/мокрый — атрибут **сигнала** (кто
  питает контур: БУ или АСУТП), а не датчика: выключатель один и тот же, у
  датчика — только коммутируемая способность. «Мокрый» — контур питает БУ
  (напряжение цепей управления), «сухой» — АСУТП.
  «Сигнала нет» — вариант датчика (пустой `emits`) или флаг, а не слот.
- **Питание цепей управления** (источник встроенный/внешний × 24 В DC /
  220 В AC) — атрибут БУ (схема цепей `CMD_WIRING`), применяется сразу к
  командам открыть/закрыть/стоп/ESD и к «мокрым» выходам; на каждый датчик
  напряжение не выбирается.

Связь «датчик выдаёт сигналы» уже есть (`emits`); ограничение «сигнал требует
датчик» выражается Правилом `require`.

> **Открытый вопрос (обсудить):** справочник «Датчик» на одном виде даёт
> много записей (технология мех/энкодер × кратность одиночный/двойной —
> ≈4 на «Концевые»; ось сухой/мокрый убрана — это атрибут сигнала, не
> датчика). Плоским списком выбирать неудобно. Склоняемся описывать оси
> **опциями слотов** (каскад коротких слотов с правилами), а не плоским
> справочником — способ представления датчика требует решения.
> - Питание контура сигнализации (мокрый от БУ / сухой от АСУТП) —
>   атрибут сигнала; «общее на вид или на каждый сигнал (осн/доп)» —
>   вопрос стороны сигналов (аналог `CMD_WIRING` для выходов).

### Сервисы (`services/`)

- `cu_matrix.py` — резолвер доступности: наследование скоупов, na-запреты,
  координаты power_supply/signal_power (схема цепей: без выбранной схемы
  строки с координатой не применяются), `resolve_control_units`,
  profile-дефолты, `validate_selection` (bundle/conflicts).
- `cu_rules.py` — движок правил (show/hide/block/require/set_default).
- `cu_package.py` — пакет конфигуратора для фронта
  `{unit, slots, options, defaults, rules, matrix}`; принимает выбранную
  схему цепей (`signal_power`) и перерезолвивает набор сигналов;
  имена опций — из типизированной нагрузки (`CuSlotOption.localized_name`
  раскрывает power/logic/heater/signal).
- `cu_report.py` — описание БУ для производителя: секции дерева с
  видимыми слотами (видимость — правила hide профиля БУ, «всё, кроме
  hide»; выключенные узлы — с пометкой ``is_active=False``), опции с
  доступностью std/opt/na.
- `cu_unit_matrix.py` — редактируемая матрица профиля БУ (вкладка
  «Редактор доступных опций»): селектор «Напряжение» (`power_supply`)
  переключает базовый профиль («— любое напряжение —», `power_supply=None`)
  и переопределение конкретного напряжения (`power_supply=X` перекрывает
  базовую строку). `std`/`opt` — upsert строки на выбранном напряжении;
  `na` на «любом» — опция недоступна для БУ (нет строки), на конкретном —
  явная na-строка, перекрывающая базовую std/opt (как в `resolve_slots`);
  `inherit` на конкретном — снять переопределение (возврат к «любому
  напряжению»). **Анти-перенаслоение**: значение на конкретном напряжении,
  совпадающее с базовым, отдельной строкой не пишется (схлопывается в
  наследование); в `build_unit_matrix` `inherited=True` также для «нет
  базовой строки = na» и для строки, повторяющей базовое значение. Для
  базового вида возвращается `has_voltage_diff` — есть ли на каком-то
  конкретном напряжении отличное от базового значение. Строки с координатой
  `signal_power` в редактор не входят (переопределения схем, задаются
  сидом/отдельным инструментом).
- `cu_export.py` — экспорт настроек БУ в xlsx (кнопка «Экспорт настроек в
  Excel» в «Редакторе БУ», эндпоинт `export-settings/`): видимые узлы —
  строками (всё, кроме скрытых правилом hide), слоты — строками с опциями
  в порядке `std:` → `opt:` → `na:` (пустые opt/na помечаются «none»);
  для узлов/слотов/опций берётся поле `description` (фолбэк name/code);
  доступность — из профильных строк матрицы типа БУ. Если по напряжениям
  нет отличий — один блок «Для всех напряжений питания привода», иначе —
  блок на каждое напряжение.

### Правила (Паттерн В) — назначение и примеры

Правила управляют **динамикой UI конфигуратора** в ответ на выбранное
значение (матрица, напротив, — статичная доступность по контексту). Форма:
`when {слот-условие, оператор, значение} → then {действие, слот-цель}`.

Действия и их отображение в конфигураторе:

- `show` — слот отображается (обычно, чтобы «перебить» `hide` с меньшим
  приоритетом);
- `hide` — слот не отображается (убирается из раздела);
- `block` — слот виден, но опции выбрать нельзя (inputs disabled);
- `require` — у слота появляется метка «обязателен»;
- `set_default` — подставляет опцию по умолчанию при выполнении условия
  (динамический дефолт; матричный `std` — статический дефолт профиля).

Примеры:

- `hide PROTOCOL when control_unit in [CU_BASIC, CU_INT, CU_INT_HR, CU_INT_L,
  CU_INT_O, CU_POSI]` — БУ без шины протокол не показываем (пустой слот);
- `set_default POSITION_FEEDBACK = POS_HART when SETPOINT = SETPOINT_HART` —
  выбор HART-уставки тянет позиционную ОС HART;
- `hide CU_POWER_SUPPLY when control_unit in [CU_BASIC, CU_INT, CU_INT_MB,
  CU_POSI]` — встроенным БУ не показываем «Питание БУ» (вводы — у привода);
- `hide MOTOR_STARTER when control_unit = CU_BASIC` — у базового БУ стартера
  нет;
- `PU_SHARED → hide CU_CABLE_GLANDS` / `PU_SEPARATE → show CU_CABLE_GLANDS` —
  универсальные правила (when_slot = CU_POWER_SUPPLY): «чьи отверстия для
  подбора КВ» — производное от выбора питания.

В «Редакторе БУ» → «Редактор доступных опций» профильные правила типа БУ
редактируются через `when_slot=control_unit` с операторами exact/in/not_in.
Универсальные правила с `when_slot` ≠ `control_unit` в профильном редакторе
не показываются — они общие для всех БУ и задаются сидом.

## 3. Фронтенд

Страница `/admin/ea-control` (`pages/admin/EaControlAdminPage.vue`) — шесть
разделов верхнего уровня:

1. **Конфигуратор опций** — редактор структуры
   (`EaControlStructure.vue`): дерево узел → слоты → опции. Редактирование
   в локальном черновике, единая кнопка «Сохранить» коммитит топологически
   (узел → слоты → опции; новые POST, изменённые PUT, помеченные DELETE).
   Удаление двухшаговое (пометка → «Сохранить»). Форма опции зависит от
   рода слота: value — kind «Значение»/«Нет» + имя/описание; object —
   выбор записи справочника-источника + чекбокс «Опция „Нет“» (без
   name/description/kind; kind выводит сервер из source слота). Форма
   слота — селектор «Источник значений» для object (список — словарь
   `CuSlotSource`; 2026-11-09: «Блоки управления» убран из списка,
   добавлен «Классы БУ» → `ControlUnitKind`, kind `unit_kind`).
   Слот перемещается между узлами селектором «Раздел» — собственный
   dropdown (`.section-picker`: кнопка + меню, пункты с отступом по
   вложенности) вместо нативного `<select>`: нативный popup в Chrome
   периодически закрывается, не закоммитив выбор (change приходит со
   старым значением, PUT сохраняет прежний раздел). У узла — свой
   «Родитель» для вложенности дерева (подписи разведены). В редакторе слота
   свои кнопки: «Сохранить» (только выбранный слот и его опции), «Копировать»
   (клон слота + опций с суффиксом `_Copy` в кодах — глобальная уникальность),
   «Удалить слот». Если удаляемый узел/слот/опция используются (матрица,
   правила, опции), сервер возвращает 409 с перечнем — фронт спрашивает
   «данные используются в …, действительно удалить?» и по подтверждению
   удаляет вместе с зависимыми записями (`?cascade=1`).
   Успех виден зелёным баннером «Сохранено»/«Слот сохранён».
2. **Редактор БУ** — `Блоки управления` (ControlUnit) / `Матрица` / `Правила`.
   В левой панели под «Фильтрами» — блок «Узлы» (тот же вид дерева, что в
   «Конфигураторе опций»): вкладка «Редактор доступных опций» показывает
   слоты только выбранного узла; при смене напряжения узел сохраняется,
   обновляются лишь слоты/значения. Подсветка опций: наследуемое значение
   (конкретное напряжение без собственного переопределения) — светло-зелёным
   + пометка std/opt/na; на «любом напряжении» опция с отличием по какому-то
   напряжению — светло-оранжевым; кнопки std/opt/na/насл. У «Отмены» —
   confirm при несохранённых изменениях. Кнопка «Экспорт настроек в Excel»
   (видна при выбранном БУ; xlsx через `export-settings/`, структура — §2
   `cu_export`).
3. **Справочники** — типизированные формы (входные/выходные отдельно),

**Редактор матрицы профиля БУ (`cu_unit_matrix`) — семантика напряжений и UX.**

- **na/inherit**: `na` на конкретном напряжении пишет явную na-строку
  (перекрывает базовую std/opt), а не удаляет; добавлено действие `inherit`
  (снять переопределение). `na` на «любом» — удаляет строку.
- **`inherited` уточнён**: «на этом напряжении нет собственного
  переопределения» — включает «нет базовой строки = na» и «перенаслоение»
  (строка, повторяющая базовое значение).
- **Анти-перенаслоение**: на конкретном напряжении значение, совпадающее с
  базовым, отдельной строкой не пишется — схлопывается в наследование
  (удаляет существующую перенаслаивающую строку).
- **`has_voltage_diff`**: для базового вида — флаг «на каком-то конкретном
  напряжении значение отличается от базового».
- **Фронт редактора БУ**: под «Фильтрами» блок «Узлы»; вкладка «Редактор
  доступных опций» показывает слоты выбранного узла (узел сохраняется при
  смене напряжения). Наследуемые опции — светло-зелёным + пометка значения;
  отличия по напряжениям — светло-оранжевым; кнопка «насл.»; у «Отмены» —
  confirm при несохранённых изменениях (правки не теряются молча).
