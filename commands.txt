Что делает скрипт

1. Проверяет запущен ли Docker и есть ли db.sqlite3
2. Временно правит .dockerignore — убирает исключение *.sqlite3, чтобы БД попала в образ. Оригинал сохраняется в .dockerignore.bak
3. Собирает образ через docker build
4. Восстанавливает оригинальный .dockerignore
5. Тегирует образ как cr.cloud.ru/<tenant>/demo-equipment:v1
6. Пушит в Artifact Registry (при ошибке подсказывает что проверить)

Для вашей задачи интеграции каталога сайта с ERP-системой (например, 1С) важно понимать, что BOM бывает двух видов:EBOM (Engineering Bill of Materials) — конструкторская спецификация. Она описывает идеальный состав изделия по чертежам (например: «Винт М5х10 DIN 912 — 4 шт.» без указания конкретного завода-изготовителя винта).MBOM (Manufacturing Bill of Materials) — производственная / закупочная спецификация. Это именно то, что нужно вам. Она содержит конкретные номенклатурные артикулы, которые лежат у вас на складе (например: «Винт М5х10 оцинкованный, поставщик "Крепмаркет", арт. KM-912-510 — 4 шт.»).
Рассуждай сейчас как конструктор систем. Давай поразмышляем о составной номенклатуре - единица которой состоит из нескольких номенклатурных единиц. Как рассчитывать цену для такой единицы? По логике, цена должна быть суммой цен компонентов. А лучше давай посмотрим шире - я хочу иметь модели сложных единиц в виде EBOM - несколько обобщенный вид и MBOM - детальный состав. Скажем Редуктор может быть просто модель редуктора, а может быть редуктор с адаптацией под другой посадочный размер. Это разные EBOM. Но EBOM может быть разложен до компонентов - редуктор один, адаптации можно собрать из разных компонентов.Или возьмем болт 8*50. С точки зрения потребителя - в комплекте должно быть 4 болта. По факту, могут потребоваться болты из нержавейки или из стали. Болты могут быть разных производителей. Посоветуй, как это организовать. Здесь нужно найти грань между детализацией и обобщением. Для сайта нужны EBOM. Для детальной спецификации и расчета цены или себестоимость нужно делать MBOM. Кроме того, я хочу чтобы MBOM собирался автоматически или при минимальном участии пользователя. Также я сечас подумал, что EBOM могут быть разной степени детализации - скажем, "Дисковый затвор с электроприводом", далее "Дисковый затвор ДУ200 с ЭО", далее "Дисковый затвор ДУ200 Абрадокс с ЭП 220В". С точки зрения архитектуры и сайта - это что-то вроде дерева

Готово. Команда для полного бэкапа:

python manage.py backup_cloudru
Файлы сохранятся в backups/cloudru/2026-06-01/ с сохранением S3-структуры путей. Там же будет manifest.json со списком всех объектов и их метаданными.
Если хочешь сначала посмотреть что будет скачано (без загрузки):
python manage.py backup_cloudru --dry-run

Только создать индекс без файлов:
python manage.py backup_cloudru --manifest-only

После бэкапа — запусти find_orphaned_files для поиска мусора:
python manage.py find_orphaned_files

Теперь можно. Полный workflow:

1. Бэкап:
python manage.py backup_cloudru
→ backups/cloudru/2026-06-01/manifest.json + все файлы

2. Поиск орфанов по манифесту (без запросов к облаку):
python manage.py find_orphaned_files --manifest backups/cloudru/2026-06-01/manifest.json

3. Если орфаны есть — сохранить их в манифест (на случай ошибочного удаления):
python manage.py find_orphaned_files --manifest backups/cloudru/2026-06-01/manifest.json --save-manifest

4. Удалить орфанов:
python manage.py find_orphaned_files --manifest backups/cloudru/2026-06-01/manifest.json --delete

Или одной командой (бэкап → поиск → удаление):
python manage.py backup_cloudru && python manage.py find_orphaned_files --manifest backups/cloudru/2026-06-01/manifest.json --save-manifest --delete

Перед --delete лучше сначала прогнать без него — посмотреть что найдётся.
