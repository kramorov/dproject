# Обсуждение архитектуры составной номенклатуры (BOM)

**Дата:** 2026-05-22

---

## Итоговый подход (к чему пришли)

**Пресеты + дерево опций как основа каталога.**

Вместо раздельных «каталог» и «конфигуратор» — единый интерфейс. Каждый пресет — это страница каталога с базовой конфигурацией (например, конкретный дисковый затвор + конкретный привод). Рядом с базовой конфигурацией — дерево опций: радиокнопки для выбора управления (соленоид / позиционер), чекбоксы для дополнительного оборудования (БКВ, фильтр-регулятор). Пользователь не запускает отдельный инструмент — он листает каталог, видит сборку, тут же доукомплектовывает и кладёт в заявку.

Пресеты генерируются из существующих таблиц соответствия (ValveToActuatorMatching и т.д.). Опции подтягиваются из общего пула совместимых товаров для данного типа оборудования.

**Модели:** Preset (узел каталога) → OptionGroup (группа опций: SINGLE/MULTIPLE) → Option (конкретный SKU в группе). Иерархия каталога — через `parent_preset` (FK на себя).

---

## Контекст задачи

Интеграция каталога сайта с ERP-системой (1С). Составные изделия: дисковый затвор + пневмопривод + редуктор + адаптеры + фитинги + управление + обратная связь.

## Ход обсуждения

### 1. EBOM vs MBOM

- **EBOM (Engineering BOM)** — конструкторская спецификация: «Болт М8×50 — 4 шт.» без конкретного производителя.
- **MBOM (Manufacturing BOM)** — закупочная спецификация: «Винт М8×50, поставщик Крепмаркет, арт. KM-912-510 — 4 шт.».

Для сайта нужны EBOM (что входит в изделие). Для закупки и расчёта себестоимости — MBOM (конкретные SKU). Между ними — слой сопоставления (matching layer).

### 2. Три типа BOM (по способу формирования)

| Тип | Описание | Пример |
|---|---|---|
| **Статический BOM** | Состав всегда одинаков, хранится в базе | Комплект адаптеров F07→F10 |
| **Шаблонный BOM** | Скелет, позиции-требования + COMPUTED-позиции | «ЗД + РД + ПП» |
| **Сохранённая конфигурация** | Результат подбора, все позиции = SKU | Конкретная сборка для клиента (MBOM) |

Одна модель `BOM`, одна модель `BOMItem`. Поле `ref_type`: `SKU | REQUIREMENT | COMPUTED`. EBOM и MBOM — это одна и та же запись в базе на разных стадиях заполненности.

### 3. Комбинаторный взрыв

20 моделей затворов × 5 приводов × 3 редуктора × 3 адаптера = 900 комбинаций. С фильтрами, распределителями, концевиками — тысячи.

**Решение:** не создавать карточки для всех комбинаций. Часть BOM-ов — вычисляемые. Каталог показывает готовые, стабильные SKU + пресеты. Остальное — через опции и авто-подбор.

### 4. Слой совместимости (interoperability)

Адаптер — это мост между стандартами посадки (ISO 5211) и спецификациями штоков:

```
MountingStandard (F07, F10, ...)
StemSpec (диаметр, тип шпонки, ...)
ValveMounting / ActuatorMounting (привязка моделей к стандартам)
Adapter (input → output по посадке и штоку)
```

Подбор адаптера — запрос, а не BOM. Совместимость — физическая реальность, вынесенная в отдельные модели.

### 5. Резолверы как обёртки над таблицами соответствия

Существующие таблицы (ValveToActuatorMatching, ActuatorToGearboxMatching) становятся источниками данных для резолверов — функций, которые на вход получают valve + actuator, на выход — список подходящих адаптеров/редукторов.

`COMPUTED`-позиция в BOM хранит не SKU, а правило вычисления. При сборке вызывается резолвер, смотрит в таблицу, возвращает SKU.

### 6. Итоговый подход: пресеты + дерево опций

Пресет = готовая страница каталога с базовой конфигурацией. Дерево опций = inline-конфигуратор на странице товара:

```
Каталог / Сборки / ABRA VF826 + пневмопривод
  │
  ├── Базовая конфигурация (пресет)
  │   └── VF826 ДУ200 + Camozzi 5N — цена от 120 000 ₽
  │
  ├── Управление (⊙ выберите одно)
  │   ├── ○ Соленоид NAMUR 5/2, 24В       +8 500 ₽
  │   ├── ○ Позиционер Siemens SIPART      +45 000 ₽
  │
  ├── Дополнительно
  │   ├── ☐ БКВ-101 (концевые)             +3 200 ₽
  │   └── ☐ Фильтр-регулятор Camozzi       +6 800 ₽
  │
  └── Итого: от 120 000 до ~170 000 ₽
```

**Границы применимости:**
- Хорошо: десятки моделей арматуры и приводов, ограниченный ассортимент опций
- Риск: 500+ пресетов в каталоге (решается иерархией через parent_preset)

## Модели данных (предварительно)

```
Preset
  ├── sku: FK → SKU (базовый SKU сборки)
  ├── name: str
  ├── base_items: M2M → SKU (обязательные компоненты)
  ├── parent_preset: FK → self (иерархия каталога)
  └── is_active, sorting_order

OptionGroup
  ├── preset: FK → Preset
  ├── name: str («Управление», «Обратная связь»)
  ├── selection_mode: SINGLE | MULTIPLE
  ├── is_required: bool
  └── sorting_order

Option
  ├── group: FK → OptionGroup
  ├── sku: FK → SKU
  ├── price_override: Decimal (nullable)
  ├── is_default: bool
  └── sorting_order
```
