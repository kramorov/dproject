# ASSY — Сборки и заказы клиентов

> Снапшот: 2026-08-13
> Статус: модель зафиксирована (кардинальность, две линии версионирования, fork)
> Связано: [`configurator.md`](configurator.md), [`ai-assistant.md`](ai-assistant.md)

## Назначение

Документ описывает, как в системе связаны три слоя:

1. **Требования клиента** — что нужно подобрать (вход).
2. **Сборка** — структура + требования + подобранное оборудование (рабочий результат).
3. **Заказ клиента** — позиции, версии, жизненный цикл (бизнес-процесс).

Оборудование бывает **базовым** (ФР, привод, БКВ, кабельный ввод, редуктор, соленоид, фитинг — продаётся как есть) и **составным** (пневмопривод-комплект, ФР+МК, привод+позиционер — собирается из базовых типов). На запрос клиента система отвечает **сборкой**: структурой из типов оборудования и конкретными позициями из БД, подходящими под требования.

## Базовые понятия

### Сборка (AssemblyRequirements)

Результат подбора: **структура + требования + выбор оборудования**. Живёт в двух состояниях:

- **`draft`** — рабочая версия. Mutable, **не версионируется**.
- **`fixed`** — закреплённая версия. Immutable. Момент закрепления = «сделали КП / счёт / пошло в работу».

### Компонент (ComponentRequirement)

Один узел дерева сборки = **один тип оборудования** + его требования + результат подбора (выбранный SKU). Компоненты образуют дерево (`parent`), которое повторяет структуру `CompositionGroup`.

### Fork (клонирование)

**Полное глубокое копирование** сборки (дерево + требования + выбранные позиции) в новую запись. Это НЕ дельта — каждая версия самодостаточна. Используется в двух случаях:

- из **типовой сборки** (шаблон → новый draft);
- при **изменениях** (требований или состава).

### Закрепление (fixate)

**Смена статуса `draft → fixed` той же записи** (без копирования). Присваивает `revision`, заполняет `fixed_at / fixed_by / fixation_comment`.

**Guard:** `fixate()` допустим только когда у **всех** узлов терминальный статус — `selected` или `skipped`. Остались `pending / requirements_filled / filtered` → отклоняется с сообщением.

### Включение компонента (`included`)

CompositionGroup описывает **все возможные** компоненты (в т.ч. составные), но не все нужны пользователю. `ComponentRequirement.included` фиксирует решение «нужен / не нужен», принятое при заполнении требований:

- `required`-группы → `included=True` принудительно;
- `optional` / `xor` → решение пользователя/AI;
- составной узел с `included=False` исключает всё своё поддерево.

`status` — следствие:
- `included=False` → `skipped` (терминальное «осознанно не нужен»);
- `included=True` → `pending → requirements_filled → filtered → selected`.

### Две линии версионирования

Требования и состав — это **две разные линии**, и они форкаются **независимо**:

- **Требования** — таймлайн версий позиции (`ClientRequestItem.parent_version`).
- **Состав** — линия сборок **под каждой версией требований** (`AssemblyRequirements.parent_assembly`).

```
Требования (таймлайн):      R1 ──► R2 ──► R3        (parent_version)
                             │      │      │
Состав (под каждым R):      A1     A4     A5        (parent_assembly — только внутри одного R)
                             │             │
                             A2            A6
                             │
                             A3
```

Правила линии состава:

- **Изменились требования** → форк требований (`R2.parent_version = R1`) + копия сборки (`A4`), привязанная к новым требованиям (`A4.requirement_version = R2`), **`parent_assembly = null`**. Непрерывность даёт цепочка требований `R2 → R1`, а не сборка.
- **Состав изменился, требования те же** → форк сборки (`A2.parent_assembly = A1`), **`requirement_version = те же R1`**.
- **Правки в драфте** → без форка, мутируем на месте.

То есть `parent_assembly` отвечает строго на вопрос «это следующая итерация состава **для тех же** требований». При смене требований составная линия обнуляется.

### Связь «сборка → требования» (направление)

Основной связью является **`AssemblyRequirements.requirement_version` (сборка → требования)**, а не обратная `ClientRequestItem.assembly`. Отсюда честные отношения:

- **1 версия требований → N сборок** (её история состава);
- **1 сборка → 1 версия требований** (неизменяемо).

Текущая сборка позиции выводится: драфт для этой `requirement_version`, а если его нет — последний `revision`.

### Кардинальность и шаблоны

- **Рабочая сборка** — привязана к одной версии требований (`requirement_version` не null).
- **Шаблон (типовая сборка)** — `requirement_version = null`, `is_template = true`. Живёт в каталоге, ни к чему не привязан.
- **Sharing («шарь, пока не изменили»)** — позиция ссылается на шаблон до первого изменения; изменение → `fork()` → своя рабочая сборка. То есть sharing реализуется через шаблоны, а не через общий `item.assembly`.

## Связи (схема)

```
ClientRequest (запрос клиента)
 └─ 1:N ─► ClientRequestItem (позиция; версии требований: version / is_current / parent_version)

AssemblyRequirements (сборка)
 ├── requirement_version ─► ClientRequestItem   (какие требования; null у шаблона)
 ├── parent_assembly ─► AssemblyRequirements     (состав-линия, только внутри одного R)
 ├── composition_group ─► CompositionGroup (структура)
 ├── root_node          ─► CompositionGroup (точка входа)
 ├── global_requirements (валидируется по ETP)
 ├── status: draft | fixed
 ├── revision: int
 ├── is_template: bool
 └─ 1:N ─► ComponentRequirement (дерево)
              ├── equipment_type ─► EquipmentType
              ├── included: bool (нужен/не нужен; False → skipped)
              ├── requirements (own/effective/cascade, по ETP)
              └── selected_sku ─► SKU   (базовый тип; composite = null, результат = поддерево)
```

Поля `AssemblyRequirements` (целевое состояние):

```
requirement_version  FK(ClientRequestItem)   # какие требования; null у шаблона
parent_assembly      self-FK                 # состав-линия: только внутри одних требований
status               draft | fixed
revision             int, null               # None у draft; итерация состава ВНУТРИ одного requirement_version
is_template          bool                    # fixed + опубликован как типовая сборка
fixed_at / fixed_by / fixation_comment       # заполняются при fixate()
composition_group / root_node / global_requirements
components           дерево ComponentRequirement   # клонируется целиком в fork()
```

## Сюжеты

### Сюжет 1. Новый запрос клиента → позиция → драфт-сборка

1. Менеджер создаёт `ClientRequest` (клиент, текст запроса, дата).
2. К запросу добавляется позиция `ClientRequestItem` (тип подбора, текст ОЛ).
3. Для позиции создаётся `AssemblyRequirements` со `status=draft`, `requirement_version=<версия позиции>`, `revision=None`, `composition_group=<шаблон структуры>`.
4. `expander` разворачивает `CompositionGroup` в дерево `ComponentRequirement` (со `status=pending`).

**Результат в БД:** `ClientRequest → ClientRequestItem → (requirement_version) → AssemblyRequirements(draft) → дерево ComponentRequirement`.

### Сюжет 2. Подбор «с нуля» (движок конфигуратора)

1. Пользователь вводит требования (или AI извлекает их из текста) → `own_requirements` / `global_requirements`.
2. `resolver` считает `effective_requirements` по приоритету `own > global > cascade`, типизирует значения по ETP.
3. `filter_engine` ищет варианты по требованиям → `filter_results` (кандидаты).
4. Пользователь выбирает продукт → `selected_sku = SKU`, `status=selected`.
5. `cascade` применяет `DerivationRule`: параметры выбранного продукта пробрасываются в дочерние компоненты (например, `actuator.port_size → solenoid.connection_size`).

**Результат:** дерево заполнено требованиями и выбранными SKU. Сборка всё ещё `draft`.

### Сюжет 3. Использование типовой сборки (шаблон)

1. В каталоге есть типовая сборка `is_template=True`, `requirement_version=null` (например, «ПП - комплект: привод + БКВ + фитинги»).
2. Менеджер берёт её для новой позиции → `instantiate_from_template()`.
3. Делается `fork()`: полная копия (дерево + требования + выбранные SKU) → новый `draft`, `requirement_version=<версия позиции>`, `parent_assembly=null`, `is_template=False`.
4. Позиция (через `requirement_version`) ссылается на новый draft.

**Результат:** новая рабочая сборка, независимая от шаблона. Шаблон остаётся нетронутым.

### Сюжет 4. ФР как базовый тип vs «ФР + монтажный комплект» в составе

- **Продажа отдельно**: позиция «фильтр-регулятор» — сборка с одной группой `required: [ФР]` (или вообще без сборки, если это просто базовый SKU).
- **В составе сборки**: группа `CompositionGroup` `required: [ФР, монтажный комплект]`. Большие сборки подключают её через `references` (ссылку на группу), а не дублируют.

Гибкость достигается на уровне **структуры (CompositionGroup)**, а не кардинальности: один и тот же тип ФР — то самостоятельный узел, то часть обязательной подсборки.

### Сюжет 5. Несколько одинаковых приводов в одной заявке

1. Клиент просит 3 одинаковых привода.
2. Создаётся **3 позиции** (`ClientRequestItem`), а не одна общая сборка.
3. Каждая позиция получает **свою сборку** (или это 3 базовых SKU, если сборка не нужна).
4. До первого изменения все три могут ссылаться на одну типовую сборку (`is_template=True`). Первое изменение в любой → `fork()` → своя рабочая сборка, привязанная к своей версии требований.

**Правило:** рабочая сборка = одна версия требований; sharing возможен только через шаблон до момента изменения.

### Сюжет 6. Закрепление сборки (КП / счёт / в работу)

1. Работа над составом закончена, draft полностью заполнен.
2. Событие «сделали КП / счёт / пошло в работу» вызывает `fixate(draft)`.
3. `status=draft → fixed`, присваивается `revision` (итерация состава внутри текущей версии требований), заполняются `fixed_at / fixed_by / fixation_comment`.
4. Сборка становится immutable: `fixed`.

**Результат:** `R1 → A1(fixed, rev 1)`.

### Сюжет 7. Уточнение клиента (изменения)

**7а. Изменились требования (→ почти всегда меняется состав):**

1. Пришли уточнения → пишем текст пользователя (в версию позиции: `request_line_text`, `change_comment`).
2. Форк требований: новая `ClientRequestItem` `version+1`, `is_current=True`, `parent_version=старая`.
3. Копия сборки: `fork(A1)` → новый draft, `requirement_version=новая версия`, **`parent_assembly=null`**.
4. Работаем в новом draft; он остаётся draft до закрепления.
5. `fixate(draft)` → `fixed` (rev 1 под новой версией требований).

**Результат:** `R1 → A1`, `R2 → A4` (A4 без `parent_assembly`; непрерывность через `R2 → R1`).

**7б. Состав изменился, требования те же (например, компонент стал недоступен):**

1. `fork(A1)` → новый draft, `requirement_version=та же R1`, **`parent_assembly=A1`**.
2. Вносим замену компонента, выбираем новый SKU.
3. `fixate(draft)` → `fixed` (rev 2 под R1).

**Результат:** `R1 → A1 → A2` (состав-линия под одними требованиями).

### Сюжет 8. Публикация типовой сборки в каталог

1. Готовая и закреплённая сборка (`fixed`) объявляется типовой: `is_template=True`, `requirement_version` снимается (null).
2. Создаётся каталожная запись в `sku`: `SKU` (артикул, цена, картинка, публикация) со ссылкой-источником на сборку.
3. Состав типовой сборки фиксируется как `MBOM` (`MBOMItem` по `CompositionGroup`/`EquipmentType` со ссылками на `SKU`).
4. Другие позиции используют эту типовую сборку через `instantiate_from_template()`.

**Результат:** «типовая сборка» = `AssemblyRequirements(is_template=True)` + `SKU` (каталог) + `MBOM` (состав). Каталожные метаданные живут в `sku`, а не в рабочей сборке.

### Сюжет 9. Просмотр истории и «откат»

1. Требования: цепочка `R1 → R2 → …` через `parent_version`.
2. Состав под каждой версией: цепочка `A1 → A2 → …` через `parent_assembly`.
3. «Откат» = создать новый draft форком из нужного исторического `A` (например, вернуться к A1, отбросив A2).

**Результат:** в любой момент восстанавливается «какой состав соответствовал требованиям версии N» и «как менялся состав под одной версией». Откат — это fork из исторического fixed, а не удаление/переписывание.

## Правила форка и закрепления (инварианты)

1. **`fixate(draft)`** — смена статуса той же записи, без копии. Событие: «КП / счёт / в работу». **Guard:** все узлы в терминальном статусе (`selected`/`skipped`).
2. **`fork(source)`** — глубокое копирование (дерево + требования + выбор) → новый `draft`. Копируется и выбор (вариант А — готовая reference-BOM).
3. **Требования изменились** → форк требований + копия сборки: `requirement_version=новая`, `parent_assembly=null`.
4. **Состав изменился, требования те же** → форк сборки: `requirement_version=та же`, `parent_assembly=предыдущая`.
5. **Правки драфта** → без форка, мутируем на месте.
6. Draft — единственный mutable объект; фиксация делает снимок immutable, дальнейшие правки — только через fork.
7. Полные снапшоты, **не дельты**: каждая версия самодостаточна; diff считается постфактум.

## Выбранный продукт: базовый vs составной (SKU)

- **Базовый тип** (ФР, привод, БКВ, редуктор, соленоид, фитинг, кабельный ввод) → `ComponentRequirement.selected_sku = FK(SKU)`. Модель продукта однозначно определяется `equipment_type`; произвольный GenericFK не нужен.
- **Составной тип** (пневмопривод-комплект, ФР+МК) → `selected_sku = null`. Его «продукт» — это разрешённое поддерево (дети со своими выбранными SKU). Если составной узел сам является каталожной позицией — он получает собственный `SKU` + `MBOM` (Сюжет 8).

Ссылка на `SKU`, а не на сырую модель продукта, даёт:
- ссылочную целостность (SKU — единый реестр номенклатуры);
- единый путь к ценам (`price`), документам, MBOM;
- «составной продукт» выражается так же, как базовый — через SKU + MBOM.

## Где хранятся требования и сборки (отдельное приложение `assemblies`)

| Слой | Приложение | Модели |
|------|-----------|--------|
| Схема требований (какие параметры, как сравнивать) | `configurator` | `EquipmentTypeParameter`, `ParameterRule`, `DerivationRule`, `ParameterBinding`, `FittingPattern` |
| Сборка + значения требований (результат подбора) | **`assemblies`** (новое) | `AssemblyRequirements`, `ComponentRequirement`, (EBOM) |
| Номенклатура + MBOM (материализация для КП/счёта) | `sku` | `SKU`, `MBOM`, `MBOMItem` |
| Заказ клиента (бизнес-процесс) | `client_requests` | `ClientRequest`, `ClientRequestItem`, `RequestSnapshot` |

Граф зависимостей (без циклов):

```
configurator (движок) ──► assemblies (результат) ──► client_requests (заказы)
                                                    ──► sku (номенклатура, MBOM)
                                                    ──► core, ai_assistant
```

- `assemblies` — домен результата, мост «результат ↔ заказ ↔ номенклатура» (`requirement_version` → заказ, `selected_sku` → sku).
- `configurator` тянет только `assemblies` (производит/читает их) — движок не зависит от заказов напрямую.
- `client_requests` не тянет ни `configurator`, ни `assemblies` (находит сборку через reverse `requirement_version`).

## Сборка, EBOM, MBOM — три уровня

- **Assembly** (рабочая сборка, draft/fixed) — инженерный подбор, источник истины в процессе.
- **MBOM** = **материализация `fixed`-сборки через `SKU`** — закреплённый вариант в номенклатуре, чтобы сборка входила в КП/счёт единообразно. **Порождается только из `fixed`-сборки** (обход дерева, `selected_sku` → `MBOMItem.sku`), не редактируется отдельно.
- **EBOM** = **зонтик над несколькими сборками** — инженерный роллап по проекту/заявке (несколько позиций → несколько сборок → один EBOM). Пока не смоделирован — отдельный шаг.

MBOM — производная от fixed, а не вторая правда: рассинхрон исключён по построению.

## Открытые вопросы / следующие шаги

Подробный пошаговый план — в [`EXECUTION_PLAN.md`](EXECUTION_PLAN.md). Ключевые пункты:

1. Новое приложение `assemblies`; перенос `AssemblyRequirements` + `ComponentRequirement`.
2. Миграция связи `ClientRequestItem.assembly` → `AssemblyRequirements.requirement_version`.
3. Поля `AssemblyRequirements`: `status`, `revision`, `parent_assembly`, `is_template`, `fixed_*`; `ComponentRequirement.included`, `selected_sku`.
4. Сервисы `fork()` / `fixate()` + ETP-валидация требований.
5. Зачистка deprecated: `PropagationRule`, `ParameterSource`, `EquipmentType.source`, старые `*Requirement`-формы.
6. MBOM — деривация из fixed; EBOM — зонтик (модель).
7. Frontend CRUD для всех моделей (Vue, не админка Django).
8. `RequestSnapshot` — полная сериализация сборки.
9. (Опционально) `copied_from` (self-FK) на сборке — точный provenance при смене требований.
