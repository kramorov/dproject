# DeepSeek TUI — руководство пользователя

## 1. Роли и как их включать

Я работаю в режиме **Agent** — сам пишу код, сам проверяю, сам правлю. Но качество зависит от того, как ты ставишь задачу.

| Роль | Когда использовать | Пример промпта |
|---|---|---|
| **Архитектор** | Перед большим рефакторингом, выбором паттерна | «Проанализируй структуру моделей X, Y, Z. Предложи способ унификации фильтров без дублирования кода. Варианты с плюсами/минусами.» |
| **Конструктор** | Создание нового модуля/страницы по образцу | «Сделай модель X с фильтрами как в Y, страницу Streamlit как Z. Фильтры: a, b, c.» |
| **Критик** | После реализации, перед коммитом | «Проверь код на баги. Найди дублирование, хрупкие места, проблемы с производительностью.» |
| **Программист** | Конкретная правка | «В build_filter_lookup замени X на Y. Не трогай остальное.» |

**Ключевое:** явно называй роль. «Подумай как архитектор…» / «Теперь как критик…»

---

## 2. Как ставить задачи нужного объёма

Я лучше всего работаю с задачами размером в **одну модель + одну страницу** или **один миксин + его использование в 1-2 моделях**.

| Объём | Пример | Результат |
|---|---|---|
| **Функция / метод** | «Добавь обработку NULL в build_filter_lookup» | Быстро, точно |
| **Модель + страница** | «Сделай DirectionValve с фильтрами и страницу solenoid_valves.py» | Хорошо, если описан набор фильтров |
| **Модуль (3+ моделей)** | «Переведи все каталоги на SmartCatalogMixin» | Риск уйти в сторону. Разбей на этапы. |
| **Приложение целиком** | «Сделай систему тендеров» | Нужен план. Сначала архитектура → модели → страницы. |

**Правило:** если задача длиннее двух фраз — попроси сначала план, потом реализацию.

## 3. Как прерывать неверные рассуждения

Если видишь в консоли (`reasoning_content`), что я пошёл не туда:

- **Коротко:** `стоп` — останавливает текущую цепочку
- **С направлением:** `стоп. Дело не в миграциях, фильтр просто не применяется. Проверь build_filter_lookup.` — я переключусь на указанную гипотезу
- **С контекстом:** `стоп. thread_diameter в БД NULL, поэтому совместимость не работает.` — я приму это как факт

Не жди, пока я закончу длинное рассуждение — прерывай сразу.

## 4. Ключевые паттерны взаимодействия

### 4.1 Данные раньше кода
```
# Плохо:
«Почини фильтр резьб»

# Хорошо:
«При выборе G 3/8 фильтр показывает 85 записей вместо 2.
Вот вывод консоли: [логи]. В БД diameter=NULL, pitch=NULL.»
```

### 4.2 Образец раньше спецификации
```
# Плохо:
«Сделай фильтр для клапанов»

# Хорошо:
«Сделай DirectionValve с фильтрами как в PneumaticFitting.
Страницу как fittings_catalog.py. Особенность: 3/2 ↔ 5/2 совместимость.»
```

### 4.3 Проверка раньше продолжения
```
# После каждой правки:
«Запусти тесты»
«Проверь, что поле есть в модели»
«Закомпить перед следующим шагом»
```

## 5. Оптимальный промпт (шаблон)

```
[Контекст — что уже сделано]
[Конкретная проблема или задача]
[Ожидаемый результат]
[Ограничения — что НЕ трогать]

Пример:
Модель DirectionValve наследует SmartCatalogMixin.
Нужно добавить фильтр function_id с совместимостью 3/2 ↔ 5/2.
Страницу делать НЕ нужно — только модель.
```

## 6. Инструменты, которые стоит использовать

| Инструмент | Когда |
|---|---|
| `checklist_write` | Перед любой задачей из 3+ шагов — я создаю чеклист в сайдбаре |
| `update_plan` | Для архитектурных решений — я показываю фазы |
| `apply_patch` | Правки в нескольких местах файла |
| `edit_file` | Одна замена в одном месте |
| `grep_files` | Поиск по коду — всегда быстрее, чем чтение наугад |

---

## 7. Работа в терминале

- **Запуск тестов:** `python manage.py test ...` — я предложу, ты подтвердишь
- **Streamlit:** `streamlit run pages/xxx.py` — запускай сам, я только пишу страницы
- **Git:** я даю команды, ты выполняешь
- **Миграции:** `makemigrations` + `migrate` — всегда вручную

---

## 8. Чего не делать

- Не проси «исправить всё» без конкретики — я пойду не туда
- Не жди, что я угадаю структуру БД — дай вывод SQL или описание полей
- Не позволяй мне гадать — если я говорю «вероятно» или «может быть», дай данные
